# 何を測って、何で止めるか

**先に決めておく。** データが出てから基準を作れば、どんな結果でも「続ける理由」が書ける。

**これはデータベースを完成させるプロジェクトではなく、支払意思を検証する Revenue Experiment である。**
Monetization Signal が出なければ、**データ件数を増やさない。**

## 測る3つ（別のものとして扱う）

| | 指標 | 取り方 |
|---|---|---|
| **到達** | unique views / clones / referrers | traffic API |
| **CTA Click** | `orders/*.md` のビュー数を**価格ごとに分離** | traffic API の `popular/paths` |
| | **0 と測定不能を分ける。**`popular/paths` は上位10パスしか返さないので、出てこない tier は「0」ではなく「10位より下」の可能性がある | 返却件数が10未満なら一覧は完全なので不在＝0。10件で飽和していたら `observable: false` として記録し、判定に使わない |
| **Inquiry** | Issue #1 の 👍 とコメント | issues API |
| **Signup** | watchers ＋ Release のダウンロード数 | repo API / releases API |

**CTA の着地を Pages ではなく repo 内の markdown にしたのは計測のためである。**
traffic API が返すのは `github.com/owner/repo/...` のパスで、
`owner.github.io/repo/...` は含まれない。**Pages に価格表を置くと、クリックが一切測れない。**

**コメント1件は 👍 10件より重い。** 用途・件数・条件を書く手間を払っているので、
👍 が0でもコメントが1件あればそれを作る。

## 観測メモ：clone は人間とは限らない（2026-09-03 追記）

公開翌日の実測。**unique views 0 / unique clones 19（総数 44）/ referrers なし /
👍・コメント・watchers・Release DL すべて 0。**

**views 0 で19の別ソースが clone しているのは、人の行動の形ではない。**
人はページを見てから clone する。ミラー・CI・クローラ・レジストリのインデクサの可能性が高い。

**閾値は変えない。** 判定に使うのは `orders/*.md` のクリックと 👍・コメント・watchers で、
**clone 数はもともと判定条件に入っていない。**
入れないままにする理由がここで実データとして確認できた、という記録である。

**同じ姉妹実験（keihyo-cases）でも同じ形が出ている。**
両方で views 0・referrers 0・clone だけが伸びているので、
**これは題材の魅力ではなく、GitHub 上の自動巡回の性質だと考えるのが妥当。**

## 14日で決めること

| 観測 | 判断 |
|---|---|
| **観測できた**クリック合計 **< 20**、かつ測定不能な tier が無い | **買い手仮説が外れ。価格の書き換えで粘らない。** 5tier を README と Pages から下げ、データセットは無償公開のみ残す（維持は月次 Action だけ） |
| 観測できたクリックが少なく、**測定不能な tier がある** | **止めない。判定を保留する。** `popular/paths` が飽和しているだけの可能性があり、**測定不能を0と読むと、届いていないことを関心の不在と誤認して自分で実験を殺す。**👍・コメント・watchers・Release DL の明示的シグナルで判断する |
| 👍 0 **かつ** コメント 0 | Inquiry ゼロ。`pricing` を削除し、`orders/*.md` を README の1行に縮退 |
| watchers **< 5** かつ Release DL **0** | Distribution が機能していない。referrers でどの経路が効いたかを見る。**チャネルを変える前に題材の適否を先に疑う** |

**どの場合も、データ件数は増やさない。** 課徴金額の構造化にも着手しない。

### 続けてよい唯一の条件

**`orders/watch.md`（月 ¥4,980）が5tier中で最多クリックを取ること。**
これが勝てば「維持工程が商品」が再現されたことになる。

- `license.md`（年 ¥120,000）が勝つ → **取り決めと構造化に払う**が確認できた。
  ただし**そこで網羅性の保証を売り始めない。** 抜けたときに何をするかの運用設計が先で、
  設計のない「保証」は売ってはいけないものを売ることになる
- `api.md` だけが勝つ → 買い手は開発者。B2Bコンプラの仮説を捨てて API / MCP 側に寄せる
- `alert.md` が勝つ → 買い手は与信・調達。公取委だけで足りるか聞く
- `onboarding.md` だけが勝つ → **一番危ない。** 契約数に比例して人手が増える唯一の商品なので、
  月2件の上限を守り、これを主商品にしない

## 30日で決めること

有償契約 **0**（Inquiry があって成約ゼロを含む）→
**HC-6「公表件数が年およそ50件規模の単一法域の監視は、単独商品にならない」として型を Kill し、台帳に記録する。**

## この Experiment の最大の弱点

**この製品そのものに払われた実績が無い。**
公表価格を確認できたのは隣接商品（法情報DBの審決全文、与信SaaSの行政処分監視、単発の調査レポート）だけである。

**「誰も取適法勧告データを売っていない」理由が「年およそ50件では商品にならない」である可能性を、
一次情報では排除できていない。**

**Aggregation Gap があることと、誰かが金を払うことは別である。**
穴が埋まっていない理由が「埋める価値がないから」であることは十分にありうる。
だから raw の完成度に投資せず、初日から価格を出して測る。

## 収益はまだ発生しない

**課金導線は作っていない。** 5tier はいずれも存在せず、価格は検討中の目安である。
測っているのは「その価格で手が挙がるか」だけ。
実際の請求・入金が発生する時点だけが Owner の操作になる。
